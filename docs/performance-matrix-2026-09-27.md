# 扩展性能测量（2026-09-27）

本轮只扩展测量程序，未改动 `src/`、协议默认值或依赖。协议基线为 `de6f726`。
结论：下一轮应优先分析**突发流量下的事件投递与调度**，目前没有足够证据支持直接改动
DELIVER 公共结构或超时索引。单连接增大窗口并不总能增加吞吐，多连接能提高吞吐，但成本也明显增加。

## 测量口径

- Windows，16 个逻辑处理器，Rust 1.98.1，release 构建。各场景顺序运行，无并发构建。
- 主矩阵与对照均为每轮 3 秒、各 2 轮，另有 3 个场景各 10 秒复测，共 45 轮。
  握手结束后所有连接、网关通过屏障一起启动；无独立预热阶段。这是定位用短测，不是容量承诺。
- `parallel=8` **每连接**；window 也按连接计。默认 spool=256、batch=64 帧/65536 字节。
- 本轮模拟网关默认 `server_nodelay=1`，客户端仍使用原来的 TCP_NODELAY 默认值。
  旧压测网关未开启该选项，历史吞吐不能直接与本表比较；`server_nodelay=0` 保留对照能力。
- 短短信为 10 字节 ASCII；长短信为 500 字中文、8 段 UCS2；DELIVER 为 100 字节 ASCII MO，
  网关保持最多 32 个未确认 DELIVER，逐个收到 DELIVER_RESP 后补发，到期停止并排空。
  本轮没有测状态报告解析或长 MO 重组。
- SUBMIT 延迟延续原压测的抽样口径：每 64 次成功调用记录返回后的时间，再与响应关联。
  **不含 submit 等待窗口的时间，快速响应可能早于采样登记而漏样，不是完整端到端延迟。**
  多连接分位数由原始样本合并计算，未平均各连接分位数。
- DELIVER 每 64 条采样，从网关编码前到客户端事件消费，含写出确认门控。
  `msg_id` 用于携带单调时钟偏移，仅适用于该进程内模拟场景。
- 吞吐按成功响应/收到事件数除以配置时长计算，包含截止时刻的最后一批排空。
  关闭失败的轮次标记为失败，不把按全时长折算的低速当作稳态吞吐。
- CPU 为 Windows GetProcessTimes 报告的整个进程用户态+内核态时间，平均核数除以进程墙钟时长；
  包含客户端、模拟网关、统计与收尾，不是协议库专属 CPU。很短或低负载进程受系统计时精度影响。
  工作集每 50ms 采样取最大值，不是精确峰值，也不是堆分配量。
- `alloc=1` 单独运行；计数器委托 System 分配器，记录成功 alloc/alloc_zeroed/realloc 的次数和请求字节。
  realloc 按新大小计一次，字节数为累计请求量而非存活内存；包括网关、统计器、排空和输出。
  插桩使用原子计数，会扰动性能；未拿这些轮次的吞吐作优化结论。

## 主矩阵结果

单位：SUBMIT 分片/秒、DELIVER 条/秒。除特别说明外为两轮均完整运行、零重试、零超时、零丢弃。

| 场景 | 第 1 轮 | 第 2 轮 | 观察 |
|---|---:|---:|---|
| 1 连接，窗口 16，短短信 | 122972 | 126163 | 小窗口也达到约 12 万 |
| 1 连接，窗口 64，短短信 | 128626 | 127136 | SUBMIT 抽样 p99 0.70–0.74ms |
| 1 连接，窗口 256，短短信 | 128379 | 129571 | 增窗收益很小，p99 2.32–2.43ms |
| 4 连接，各窗口 64 | 338896 | 335629 | 总吞吐约单连接的 2.6 倍，p99 1.18–1.20ms |
| 4 连接，各窗口 256 | 321198 | 失败 | 第二轮 2 条连接提前关闭，不能视为稳定配置 |
| 延迟 50ms，1 连接，窗口 64 | 1027 | 1027 | 抽样 p50 约 62ms，计入定时器/调度开销 |
| 延迟 50ms，1 连接，窗口 256 | 4099 | 4184 | 扩窗约 4 倍收益 |
| 延迟 50ms，4 连接，各窗口 64 | 4191 | 4107 | 相同总窗口得到相近吞吐 |
| 长短信，默认 300s 冷却 | 2048 段后停止 | 2048 段后停止 | 每轮 256 条全部响应，引用耗尽；不是持续速率 |
| 长短信，合成冷却 1ms | 116592 | 115365 | 约 1.44–1.46 万条长短信/秒 |
| 纯 DELIVER，窗口 32 | 123864 | 126004 | DELIVER p99 0.32–0.34ms |
| 混合 SUBMIT + DELIVER | 86029 + 43431 | 84402 + 42638 | SUBMIT p99 1.12–1.17ms，DELIVER p99 0.37–0.39ms |

默认长短信轮次的 `exhausted=1` 是资源边界，`closed=0`；683 分片/秒只是将 2048 段除以 3 秒，
不能用作长短信稳态吞吐。1ms 冷却仅隔离编码/传输成本，不是生产参数建议。

## 突发与网关配置对照

| 对照 | 完整运行 | 结果 |
|---|---|---|
| 网关 TCP_NODELAY=0，纯 DELIVER | 0/2 | ChannelClosed，内部事件深度峰值均 257 |
| 网关 TCP_NODELAY=0，混合流量 | 0/2 | ChannelClosed，峰值 295 / 280，终态与确认未全部完成 |
| 网关 TCP_NODELAY=0，短短信窗口 16 | 1/2 | 完整轮仅 27351 分片/秒；另一轮提前关闭 |
| 4 连接窗口 256，spool=1024 | 2/2 | 347200 / 349023 分片/秒，零丢弃 |
| 纯 DELIVER，spool=1024 | 2/2 | 125272 / 125639 条/秒，与默认容量同量级 |
| 混合流量，spool=1024 | 2/2 | 85351+43076 / 85960+43392，与默认容量同量级 |

早期网关未启用 TCP_NODELAY 的试跑也重现了 DELIVER 提前关闭，但未纳入正式表格。
正式对照只改变网关选项，说明**报文到达节奏会影响积压稳定性**，不能仅用平均吞吐解释。
结合 `reserve_deferred_event` / `emit_event` 的深度检查，这些现象与内部事件积压关闭路径一致；
本轮没有采集调度栈，尚不能断言具体哪个锁、任务或分配是主要耗时来源。
深度峰值还含关闭时的终态批次，不能把 511 等收尾峰值解释为正常队列容量。

扩大 spool 在本次对照中改善了完整运行比例，但额外两轮不足以保证稳定性，且没有普遍增加吞吐。
因此未改默认容量，也未依据这组结果直接实施批量事件投递。

| 纯 DELIVER | 0 | 124968 | — | 0.337ms | 2.87 | 7.11 MiB |
| 混合流量 | 83998 | 42412 | 1.235ms | 0.413ms | 3.16 | 7.31 MiB |

三轮均全量响应/确认/事件一致、零重试、零超时、零丢弃。单连接窗口 64 短短信的 3 秒轮次占用
约 3.33–3.47 核；四连接约 9.27–9.43 核，说明本机进程总吞吐扩展不是线性的。
网关自身逐帧写入、系统调用与 Tokio 调度均包含在成本内，不能据此认定协议库已达到 CPU 上限。

分配插桩轮次使用 spool=1024，各两轮计数比率一致：

| 场景 | 每个成功分片/事件的分配与重分配次数 | 累计请求字节/分片或事件 |
|---|---:|---:|
| 短短信 | 约 15.0 | 约 477 |
| 8 段长短信 | 约 7.5 | 约 1159 |
| 100 字节 DELIVER | 约 12.0 | 约 628 |

长短信换算每条约 60 次、9272 字节。这些是**整条模拟链路**的成本，DELIVER 的网关端 clone/encode
也在其中，不能把 12 次全部归给客户端解码。若后续考虑 Bytes API 变更，应先隔离库内分配或做剖析。
