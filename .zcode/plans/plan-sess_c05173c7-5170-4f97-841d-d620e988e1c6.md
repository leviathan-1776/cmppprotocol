## 一、分析结论摘要（完整报告将在批次 0 落盘为 docs/code-analysis.md）

### 架构现状
- 每连接 5 个长驻 task：writer / reader / heartbeat / timeout 扫描 / 事件 dispatcher（detached）。TCP `into_split()`，双写通道（submit 容量 1000 + control 256，writer 内 biased select + control 突发上限交替防饿死），事件两级转发：spool(258, 含内嵌 oneshot 工单) → 单 dispatcher → events(1000)。
- 上一个 perf 提交（cc82949）已完成：parking_lot 锁替换（临界区无 await）、writer 批量合并单次 `write_all`（≤64 帧/64KB）、`SubmitOptions` 模板化消除逐段 String clone、UDH 池 4096 分片、窗口准入后才惰性编码分片、窗口上限 256→16384。
- 正确性工程质量高：attempt 状态机（Queued→Writing→AwaitingResponse→RespondedWhileWriting）、seq 永不复用 + retire 区间隔离、UDH 引用三重隔离（active 位图 / 300s cooling / 随机起点）、超时预算从"完整写出"起算、`decode_eof` 截断帧检测、DELIVER 未写出 RESP 就不发布事件。

### 性能瓶颈（按本地低延迟场景优先级排序）
1. **【高】事件分发管线**：每个事件 1 次 oneshot 堆分配 + spool/events 双跳 channel + 单 dispatcher 串行（`make_event_ticket` connection.rs:1008-1022、dispatcher 2088-2151）。loopback 368k segments/s 的现行上限即受制于此（README 自认）。
2. **【高】writer 批内逐帧锁**：批量 write_all 消除了 syscall，但 `claim_submit_attempt`（connection.rs:2314）与 `complete_submit_attempt`（connection.rs:2418）仍逐帧抢 `pending_submits.write()` + `submit_admission`——一条 SUBMIT 生命周期共 4 次写锁（插入/领取/写完/响应删除），多生产者 + 大窗口下为最大串行化点。
3. **【中】reader 侧 SubmitResp 逐条写锁删除**（connection.rs:2485-2504），未随读批次合并。
4. **【低】** DELIVER 解码每条 ~5 次堆分配（pdu.rs:580-605）；timeout 全表扫描持读锁（2864-2881，window=16384 时约百微秒/秒，实测影响小）；每次 read 包一层 timeout timer。

### 数据完整性（网络波动场景）
- **强项**：迟到响应三态匹配严谨（RespondedWhileWriting 不重复发事件 / Queued 命中自动抵消排队重传 / 未知 seq 仅 debug 日志），迟到响应不可能污染新 pending（seq 不复用）；内部重传复用同一 `Bytes` 包（同 seq、同 UDH ref）。
- **问题**：
  1. **【高】拆连事件洪峰**：`fail_all_pending`（connection.rs:888-905）同步循环逐条 `try_send` 进 258 容量 spool——window=16384 拆连时大部分 `SubmitDropped` 被静默丢弃（仅 `events_dropped` 计数，无日志），"每个 seq 恰好收到一个终态"的承诺在大窗口下被打破，调用方对账断裂。
  2. **【中】错误分类缺失**：UDH 引用耗尽是瞬态条件（受 300s 冷却约束）却归类 `Error::Config`；`Error` 无 `is_retryable()` 分类（Io/Timeout 可重试、Auth/Config 不可，知识散落在文档）。
  3. **【中】** `Event::SubmitTimeout` 不携带已重试次数，调用方难以评估 at-least-once 重复风险（超时重发可能重复，协议固有，决定权已正确交给调用方）。
- **测试缺口【高】**：超时重传（`submit_retries`/`SubmitTimeout`）、乱序响应、`result != 0`、慢消费者 1s 有界关闭、心跳耗尽拆连——全部无测试；mock ISMG 无延迟/丢响应/乱序注入能力；connection.rs 3042 行零单元测试。

## 二、实施批次（每批独立测试验证 + git 提交）

### 批次 0：分析报告落盘
新建 `docs/code-analysis.md`（中文，约 600 行）：任务模型与数据流图、热路径逐段分析（带 file:line）、每消息锁/分配清单、完整性机制清单与边界、测试与配置缺口、测量基线。内容基于本次已验证的分析结论。

### 批次 1：热路径吞吐（P0，对应瓶颈 1/2/3）
- **1a. writer 批内锁合并**：重构 `writer_task` 组批循环（connection.rs:2249-2363）——先收集整批帧（drain marker / open_only / cancel / 预算等无锁检查保持在收集阶段），新增批量版 `claim_submit_attempts(&[SubmitAttemptKey])`：单次 `pending_submits.write()` + admission 锁内完成整批 Queued→Writing 校验与转移，返回保留位集，未领取的帧从批中剔除后再拷贝写出；写出成功后同理新增 `complete_submit_attempts(batch, written_at)` 单锁完成整批 Writing→AwaitingResponse。效果：每消息 4 次写锁 → 2 次（插入 + 响应删除）+ 每批 2 次摊销。
- **1b. 事件直通路径**：`EventSpoolItem` 新增 `Direct { event }` 变体——立即发布的事件（reader 的 SubmitResp、timeout 的 SubmitTimeout、拆连的 SubmitDropped）不再走 oneshot 工单，直接携带 Event 进 spool，dispatcher 收到即转发，消除每事件 oneshot 分配与一次 channel 跳转；保留 Deferred(oneshot) 路径仅用于 DELIVER（其"RESP 写出后才发布"的写门控语义不变）。spool FIFO 顺序保持全局事件序。admission/深度计数/有界关闭语义全部保留（Direct 同样占 depth 名额）。
- **1c. reader SubmitResp 批量匹配**：reader 帧循环内累积同批 SubmitResp（seq, msg_id, result），单次写锁批量移除 pending 条目后统一发事件；遇到 DELIVER 帧先 flush 累积，保持事件相对顺序。
- 验证：现有 5 个集成测试全绿；loadtest loopback（window=256, parallel=8）吞吐对比基线 368k segments/s；新增事件管线基准。

### 批次 2：数据完整性（P1，对应问题 1/2/3）
- **2a. 拆连终态事件分批（已随批次 1 实现）**：`fail_all_pending` 按 128 条/批打包为 `EventSpoolItem::Batch`（depth 按事件数计），16384 个在途分片占 128 个 spool 槽。已有事件仍可能占满 spool，采用有界重试；批量入队不等于保证消费者收到。补齐投递失败的首条事件漏计。
- **2b. 错误分类**：新增 `Error::ResourceExhausted`（UDH 引用池耗尽等瞬态资源不足），与 `Error::Config` 区分；`Error::is_retryable() -> bool` 辅助方法 + 文档化分类表。
- **2c. `Event::SubmitTimeout` 增加 `attempts` 字段**（包含首次的完整写出次数），帮助调用方评估重复风险。
- 验证：最大窗口 16384 正常消费时全部 SubmitDropped 唯一送达；消费者停滞时有界退出且丢弃计数等于缺失终态数；首次及重传两次后 attempts 分别为 1 和 3；UDH 耗尽返回 ResourceExhausted 且 is_retryable 为真。运行状态见当前进度。

### 批次 3：配置与可观测（P2，已实现并验证）
- `CmppProtocolParams`：`event_backpressure_timeout_ms` 默认 1000、`event_spool_capacity` 默认 256（实际 ≥ ceil(window/128)，另留 2 个紧急槽）、`write_batch_max_frames` 默认 64、`write_batch_max_bytes` 默认 65536（完整帧可超出阈值）、`tcp_nodelay` 默认 true、`tcp_keepalive_secs` 默认 Some(60)、`tcp_keepalive_interval_secs` 默认 10。
- `ConnectionMetrics`：`write_batches` 与 `write_frames` 仅统计握手后完整写出成功的批次及协议帧，含控制帧和重传；`event_depth_peak` 按内部工单持有事件数计，含 dispatcher 当前/尝试投递/Terminal，不包含公开队列缓存。
- loadtest 新增参数 `batch_frames`、`batch_bytes`、`spool_capacity`、`event_timeout_ms`，输出新指标及平均批大小。
- 新增配置非法值、TCP 开关实际套接字状态、自定义背压预算与 Terminal 预留槽、工单深度释放保留峰值、单帧/单字节阈值的完整帧发送及指标核对用例。静态核验结果见当前进度，不将编译检查等同于测试通过。

### 批次 4：故障注入与测试基建（P3，已补齐并验证）
- `tests/common/mod.rs`：支持响应延迟、每 seq 丢弃前几次响应/全部丢弃、批量逆序响应、非零结果码、忽略心跳；独立到期队列避免延迟阻塞读帧与心跳，FramedRead 避免 select 取消读操作丢失半帧。观测记录用于用例同步，Drop 中止后台任务，正常收尾传播任务 panic。
- `tests/fault_injection.rs`：两轮满窗口逆序失败响应与窗口释放；首次响应丢失后原 seq/原报文重传且只完成一次；迟到重复响应不追加终态；心跳重传预算耗尽后在途分片全部 SubmitDropped；网关保持在线且消费者停滞时默认背压预算关闭、缺失终态与丢弃计数一致。
- `src/connection.rs` 的测试模块：在实际写出首次 SUBMIT 后，显式注入 Queued attempt 2，先处理迟到响应再调用 writer 批量领取，验证旧 attempt 被剔除、重复响应不重复发布终态。此项是状态级竞态验证，不声称真实 socket 调度下重现同一竞态。
- 批次 2 的超时次数/预算耗尽和最大窗口拆连用例继续保留。核验目标为 `cargo test` 全绿；当前运行核验已通过，详见性能核验记录。
